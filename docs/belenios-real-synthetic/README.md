# Real Belenios synthetic election

These public records were generated by the native Belenios 3.3.0 command-line tool built from upstream commit `337887bd1862c7cd057080b530fd80941bfc3c69`. The election has one synthetic voter, two candidates, and one synthetic trustee. Candidate A received one vote. The entire election is test data.

With only one voter, the published tally reveals that voter's choice. The trustee also has the full decryption key in this demonstration. This is deliberately a minimal synthetic test, not evidence of privacy in an actual election.

The precise generation, ballot verification, closing, tally, and official verification commands are in [the demo script](../../backend/scripts/belenios_synthetic_demo.sh). This is the invocation used in Ubuntu WSL, from the workspace root:

```sh
bash backend/scripts/belenios_synthetic_demo.sh \
  /tmp/votevault-belenios-linux/_run/tool-debug/bin/belenios-tool \
  /mnt/c/Users/mailp/OneDrive/Desktop/VVT/docs/belenios-real-synthetic
```

The script requires a **new** output directory; use a different path to repeat it. The original tool build and synthetic private working files were under `/tmp` and were cleared when WSL restarted. A persistent native-only tool is now available at `/root/.local/share/votevault-belenios-3.3.0/_run/tool-debug/bin/belenios-tool` in WSL. [The saved verifier script](../../backend/scripts/verify_saved_belenios.sh) reruns the official checker on the exact public archive. Private credentials and trustee material are not included in these public artifacts and must never be used for real elections.

* `election.bel`: the actual completed Belenios archive; `official-verifier.txt` records the original official check and `official-verifier-rerun.txt` records the rerun after rebuilding the persistent tool. `receipt.txt` is the encrypted ballot tracker.
* `missing-tally.bel`: the real archive stopped before tallying. `missing-tally-official.txt` records that the upstream verifier prints both `no result to check` and `all checks passed`. Our reader raises `IncompleteArchive`.
* `duplicate-credential.bel`: a separately tallied archive with two real encrypted ballots made with the same credential. Belenios accepts this under its normal replacement-vote behavior, as `duplicate-official.txt` shows. Our reader rejects the repeated credential to enforce the proposed first-ballot-only policy.
* `reader-test-output.txt` records the real-archive integration checks, including missing nested tally data in an altered copy. `demo-output.txt` records the original tool invocation's output.
* `announced-result.json` is the synthetic public result supplied independently to the standalone checker. The anchor manifest contains only the exact archive/configuration/credential commitments, ballot hashes, and derived credential tags; it contains no private trustee material.

## Synthetic chain-anchored verifier demonstration

The project now includes a standalone Belenios verifier adapter and a local-only anchor procedure. This remains a test harness, not a VoteVault production path. The anchor records exact archive bytes, the Belenios election/trustee bytes, the credential-set bytes, and every ballot hash plus a tag derived from its public credential. The script then checks the official Belenios proof verifier, the separately supplied result, receipt inclusion, the sealed archive digest, every anchored ballot, and the pinned chain/contract code reference. The local Hardhat option is solely for this synthetic test.

Terminal 1, from the repository root:

```powershell
Set-Location blockchain
.\node_modules\.bin\hardhat.cmd node --hostname 127.0.0.1 --port 18546
```

Terminal 2, from a second PowerShell window at the repository root:

```powershell
.\backend\scripts\run_belenios_anchor_demo.ps1
```

The script saves a new `chain-reference-<id>.json` and `standalone-verifier-output.txt`. It expects the persistent WSL CLI at `/root/.local/share/votevault-belenios-3.3.0/_run/tool-debug/bin/belenios-tool`; override `-BeleniosTool` or `-WslDistro` if yours differs. The configured local RPC is pinned consistently to `http://127.0.0.1:18546` in both the deployment and verifier. If any check is missing or mismatched, the process exits nonzero and does not report an overall PASS.

After the honest run, use the exact generated chain-reference path for altered-copy checks:

```powershell
.\backend\scripts\run_belenios_tamper_tests.ps1 -ChainReference .\docs\belenios-real-synthetic\chain-reference-<id>.json
```

The generator creates four separate, re-hashed copies: unauthorized ballot insertion using an unissued credential, ballot deletion, ballot ciphertext modification, and a manipulated result with the Belenios member/event hashes recomputed. Every copy must be rejected against the original sealed archive hash; the manipulated result must also differ from `announced-result.json`, and the official Belenios verifier must validate the tally evidence. The script saves each complete verifier report in a new `.local\belenios-tamper-*` directory. These checks exercise the actual verifier; they do not claim that the relayer itself validates Belenios proofs before publishing.

The formats are deliberately versioned: configuration hash is `keccak256("VV_BELENIOS_CONFIG_1\\0" || election.json bytes || 0x00 || trustees.json bytes)`; credential hash is `keccak256("VV_BELENIOS_CREDENTIALS_1\\0" || credentials.json bytes)`; archive hash is Keccak-256 of exact `.bel` bytes; ballot ID/hash is Keccak-256 of exact raw ballot JSON bytes; credential tag is Keccak-256 of the Belenios public credential UTF-8 bytes; receipt inclusion uses the Belenios SHA-256/Base64 tracker. The contract does not validate these semantics when accepting a write; the verifier recomputes and reconciles them.

This synthetic anchor does **not** integrate ballot submission, credential issuance, frozen-roster enrollment, or sealing into VoteVault. An administrator/registrar who adds false eligible credentials before the set is frozen remains a trust limitation. A malicious authorized relayer can submit an arbitrary tag; it cannot make an invalid Belenios proof pass, but it may cause denial of service. Do not interpret the `PrivateElectionArchive` contract alone as an eligibility or vote-validity oracle.

The reader's success covers archive structure and the extra duplicate-credential rule; it does not validate Belenios's cryptographic proofs. The upstream verifier performs the proof checks but allows replacement votes and untallied archives. Neither the official verification nor this reader establishes an independently anchored VoteVault election record or completes Question 07.

## Regression commands

From the repository root in PowerShell, run the focused real-archive and verifier tests:

```powershell
$env:VOTEVAULT_TEST_DATABASE_URL='sqlite:///C:/Users/mailp/OneDrive/Desktop/VVT/.local/review-test.db'
$env:VOTEVAULT_BELENIOS_ARTIFACTS='C:/Users/mailp/OneDrive/Desktop/VVT/docs/belenios-real-synthetic'
$env:PYTHONPATH='backend'
.\.venv\Scripts\python.exe -m pytest backend/tests/test_belenios_archive.py backend/tests/test_belenios_real_archive.py backend/tests/test_belenios_verifier.py -q --basetemp .local/pytest-temp
```

The complete backend regression command uses the same environment and substitutes `backend/tests` for the three test file paths. Contract permissions, duplicate credential tags, wrong-election writes, and sealed-state behavior are covered by:

```powershell
Set-Location blockchain
.\node_modules\.bin\hardhat.cmd test
```

Run the frontend build separately with `Set-Location frontend; npm run build`. The UI is not connected to the Belenios mode yet.
