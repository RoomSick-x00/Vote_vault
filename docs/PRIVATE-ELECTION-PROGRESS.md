# Private election implementation: incomplete

This document describes work in progress, not an operational private voting mode. No existing election data has been migrated. The plaintext ballot API and synthetic recount remain legacy test-only paths. Do not use any mode for real elections.

## Candidate voting protocol and integration boundary

The candidate is Belenios, rather than a home-grown proof or encryption scheme. Its documented system uses client-side ElGamal encryption, encrypted ballot validity proofs, credential-signed ballots, homomorphic tallying, and proofs of correct decryption. An independently run `belenios-tool election verify` verifies the Belenios election archive. See the [Belenios protocol overview](https://www.belenios.org/howitworks.html), [auditor instructions](https://www.belenios.org/instructions.html), and [software releases](https://www.belenios.org/software.html).

The selected integration target is official Belenios **3.3.0**, tag `3.3.0`, commit `337887bd1862c7cd057080b530fd80941bfc3c69`, downloaded into ignored `.local/belenios-3.3.0`. The native command-line tool has been built and used on synthetic records; release-signature verification and the web/server toolchain remain outstanding. The tag-signature check reports signing-key fingerprint `6DE24E97ECA886CC56E6250E21B8EEF1B1893081` but cannot verify it because the public key is absent; obtain and authenticate it independently before relying on the signature. The upstream license is AGPL-3.0 and must be reviewed for the intended distribution. Ubuntu 24.04's configured package index offers Belenios `2.2+git10-gbb6b7ea8+dfsg-1`; this predates Belenios's documented 2.5.1 threshold-key security fix and is not selected. The 3.3.0 installer describes approximately 3.3 GB and 30 minutes for an isolated OCaml bootstrap. Its build prerequisites were installed in the existing Ubuntu WSL environment; the source and toolchain build are isolated under `/tmp`.

The intended boundary is: an independent credential authority issues one election credential per eligible student; trustees hold separate decryption shares; the browser constructs Belenios ballots locally; the acceptance service verifies the actual Belenios ballot and credential before anchoring it. Election and credential-set commitments must be independently fixed before ballots are accepted. A public archive must contain the exact Belenios records and enough data to reconcile every ballot with the chain. The independent verifier must run the real Belenios proof verification, verify the archive against a pinned chain and frozen configuration, reject repeated credentials, check the published tally, and offer receipt inclusion. No such integration currently exists.

Belenios ordinarily supports replacing a vote. The 3.3.0 source's `src/tool/tool_election_data.ml` verifies ballot credentials and proofs, then `collect_ballots` filters repeated credentials when constructing the effective ballot set. A successful upstream verification therefore must not be assumed to prove this project's stricter first-vote-only policy. This project requires rejecting a second ballot for the same verified election credential at acceptance, and the standalone checker must independently reject repeated credentials in the **raw archive**, including relayer-inserted ones. Do not trust an externally supplied tag without binding it to the verified credential in the ballot. This integration has not been implemented or tested.

The upstream `src/tool/tool_election.ml` verifier also permits an election with no result and prints `no result to check` before `all checks passed`. Therefore, a zero exit status by itself is insufficient for Question 07: the wrapper must require a completed archive containing the result and decryption evidence, return INCOMPLETE when those are absent, and separately compare the announced result with the verified result.

`backend/app/services/belenios_archive.py` contains a structural reader for 3.3.0-style homomorphic election archives. It checks member hashes, event linkage and heights, duplicate member names, referenced data completeness, and absence of orphan data; it detects repeated credentials across raw ballot events, requires result and decryption events, and derives ballot trackers. Tests use real Belenios archives documented in [the synthetic election record](belenios-real-synthetic/README.md). The first real test revealed that archive event references use lowercase hexadecimal, while public ballot trackers use unpadded Base64; the reader and fixtures were corrected. This reader alone cannot establish eligibility, proof validity, a correct tally, or a chain anchor.

`backend/scripts/verify_belenios_election.py` is a separate-process checker that requires no VoteVault database or admin settings. It returns named PASS/FAIL/INCOMPLETE checks for archive structure, a supplied receipt tracker, a separately supplied result, the official Belenios 3.3.0 CLI output, and a chain anchor. It fails closed when the archive lacks a tally or the official checker does not confirm a completed election. `blockchain/scripts/check_belenios_anchor.js` uses pinned ethers 6.13.5 calls to compare the exact archive hash, frozen election/trustee and credential commitments, all ballot hashes/tags, and the sealed ballot count. In local Hardhat mode it also checks that the configured RPC URL equals the pinned RPC URL. `prepare_belenios_anchor.py` and `anchor_belenios_demo.js` create a public-only anchor for the saved synthetic election; `run_belenios_anchor_demo.ps1` documents the complete invocation. This harness is not connected to VoteVault election management or live ballot acceptance.

`backend/scripts/make_belenios_tamper_copies.py` creates four new altered archives while preserving/recomputing their member hashes and event links; it does not overwrite the source. `run_belenios_tamper_tests.ps1` runs those copies through the same official verifier and pinned chain checker and requires each to fail against the original sealed archive. This is test tooling; it has not been executed with the corrected RPC pin from this turn. Run the commands in [the synthetic election record](belenios-real-synthetic/README.md), then save and inspect their actual output before claiming those attacks demonstrated.

Privacy depends on credential issuance and trustee separation. A registrar who retains an identity-to-credential map can link identity to the corresponding encrypted ballot; trustees with sufficient decryption shares could then learn choices if they collude or decrypt individual ciphertexts. Browser compromise, logging, network metadata, voting times, small electorates and coerced disclosure also remain risks. Dishonest enrollment before the eligible set is fixed is a separate assumption. The selected release, trustee threshold, credential distribution, archive formats, first-vote policy and data retention design need explicit validation before claims can be made.

## Implemented anchor foundation

`blockchain/contracts/PrivateElectionArchive.sol` is a new, separate, undeployed contract. It fixes opaque configuration and eligibility-set hashes before opening, records unique ballot IDs and unique credential tags, and seals an archive hash and exact count. It does **not** implement Belenios or verify proofs, credentials, encryption, pending jobs or the archive contents. Any authorized relayer can still submit a fake fresh tag; the tests demonstrate this. This contract is not wired into the application, and none of its tags or byte formats should be considered final until tested against the chosen Belenios release.

The contract's mappings and events allow an auditor to reconcile distinct ballot IDs, ballot hashes, and tags against the sealed chain state, provided a verifier actually performs that reconciliation. A sealed hash alone does not establish archive availability, correctness or eligibility. The intended archive digest is Keccak-256 of exact published archive bytes; canonicalization and Belenios file layout remain to be specified and tested. The old contract and old election records are unchanged.

## What still blocks the definition of done

A native Belenios 3.3.0 executable has generated and officially verified a small synthetic election, and the rebuilt persistent executable has rerun the official verifier on an exact byte-for-byte copy of the saved archive. The new adapter and local anchor/tamper harness are code-complete enough for the next synthetic run, but the current saved execution output does not yet prove an overall end-to-end PASS with the corrected RPC pin. This is not a VoteVault election. Browser-side Belenios encryption, secure credential issuance, VoteVault ballot-proof acceptance, pre-open eligible-set anchoring, application publication/sealing integration, and final-mode UI remain unimplemented. The five attack reports still need to be run and checked. An overall VoteVault verification must remain INCOMPLETE until the actual full-path outputs pass.

The isolated build used `BELENIOS_SYSROOT=/tmp/votevault-belenios-sysroot OPAMYES=1 OPAMJOBS=2 ./opam-bootstrap.sh` from `/tmp/votevault-belenios-linux` under Ubuntu WSL. The full bootstrap failed in WebAssembly compilation with `sh: 1: wasm-merge: not found`, and in Ocsigen server installation with `install: invalid user '-g'`. The native command-line tool was subsequently built successfully with `source env.sh && make build-debug-tool`; the web/server toolchain remains incomplete. The initial source copy made on Windows had CRLF scripts and could not run; a direct Linux checkout corrected that issue. The upstream bootstrap refuses an existing sysroot, so inspect its state before attempting to restart it; do not delete it without checking its contents and path.

WSL later cleared `/tmp`, removing the temporary executable and synthetic private working files; the public records were retained in the workspace. A persistent native-only rebuild now succeeds under `/root/.local/share/votevault-belenios-3.3.0` with the isolated OPAM switch at `/root/.local/share/votevault-belenios-native/opam/5.4.1`. OPAM initially failed to fetch `ca-certs.1.0.1` with `curl ... exited with code 35`; the already downloaded package was confirmed against OPAM's SHA-256/SHA-512 and installed from the persistent download cache. The following build attempt initially stopped with `/bin/sh: 1: dune: not found` because the OPAM environment was not loaded; explicitly evaluating the persistent switch environment fixed it. The exact saved `election.bel` was copied to a separate verification directory, byte-compared, and rerun through the rebuilt upstream verifier. Its matching SHA-256 and current output are recorded in [the synthetic election record](belenios-real-synthetic/README.md). The original full bootstrap still has the separate WebAssembly (`wasm-merge`) and Ocsigen (`install: invalid user '-g'`) failures; only the native CLI is available.
